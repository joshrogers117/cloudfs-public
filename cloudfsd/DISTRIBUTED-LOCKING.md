# Cross-device file editing

The production daemon reserves an exclusive whole-file lease when an application opens a file for writing. Read-only opens remain available on other Macs. A second writer receives an SMB sharing violation before its bytes enter the local write journal. Whole-file manifest publication remains serialized: disjoint byte-range locks do not make concurrent disjoint writes safe, and a second writable open can still be denied before it requests a range lock.

Each HTTP gateway client carries a random `X-CloudFS-Client-ID` UUID for its lifetime. The backend combines it with the authenticated account identity. Two Macs signed into the same account are therefore separate editors. This header does not replace authentication or permissions. A restarted daemon has a new identity; a crashed process's leases expire after at most 60 seconds.

The coordinator renews leases every 20 seconds, uses a monotonic local deadline with a safety margin, and shares a lease across all local writable handles for that inode. The lease remains held while encrypted blocks upload. Final CLOSE or a dropped SMB connection removes the handle reference; release happens only after the pending file reaches its upload barrier. Fenced DELETE cannot remove a newer lease.

Every staged write carries the lease fence and the metadata version it was based on. The uploader validates the current local lease again immediately before committing the block map. The gateway independently rejects stale fences and stale versions. Extended-attribute writes/deletes carry the same fence. New object PUT requests declare their owning inode for folder permission checks before any manifest refers to the object.

Renewal failure is sticky. The daemon stops admitting new writes and rejects commits under the lost lease. Acknowledged local bytes remain in the checksummed journal and the Recovery interface can export them or explicitly retry after the editing application closes its handles. Retry retains the original expected version, so it cannot silently overwrite a newer remote file. Crash replay obtains a new lease but still commits with its original expected version.

Directory lookup misses refresh a cached listing before reporting “not found”; a newly created file on another Mac should not remain hidden behind the local directory cache. A writable open refreshes metadata after acquiring its lease, so it starts from the previous editor's final committed version rather than an old directory listing.

## Handle-owned byte ranges

Explicit SMB LOCK now uses a separate distributed range lease keyed by inode, authenticated client identity, and the globally unique SMB handle. Shared ranges can coexist across Macs; exclusive ranges reject every overlapping lock from another handle, and disjoint ranges may coexist. READ and WRITE enforce those ranges, including cached reads and handles that never acquired a lock. Exact unlock, CLOSE, connection loss, and filespace shutdown release their own ranges. UInt64 offsets travel as decimal strings so JSON cannot round a lock boundary. Multi-range acquisition is atomic. A lost or expired range stays failed until the application closes/reopens the handle; it cannot silently reacquire or bypass the loss through a read permit.

A new exclusive SMB LOCK also rejects an overlapping lock on its own handle, including an exact duplicate. This matters on macOS, where separate local processes can share one SMB FID. Successful repeated shared locks each require an exact unlock; the remote range remains held until the last local reservation is released. Unlock batches cannot consume more reservations than exist, and a failed remote acquisition rolls back only that request's local reservations. Shared locks forbid writes through every handle, including their owner; exclusive locks permit their owner's I/O. Local shared multiplicity is bounded to 256 reservations per handle and 4096 per inode. Exact same-range shared/exclusive stacking is still rejected conservatively; nonidentical shared ranges may overlap their owner's exclusive range. These rules follow [MS-FSA lock conflict checks](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/124bb289-eeef-4653-b9c6-4fb93dd07a21) and [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex). HTTP acquire retries retain their separate idempotent union semantics.

Range leases renew every 20 seconds and expire after at most 60 seconds. A legacy whole-inode writer lease refuses any remote range holder; acquiring ranges refuses another client's writer lease. Metadata delete/rename/replacement and publication also reject other clients' ranges. Range fences and legacy shared-mode fences cannot authorize a manifest commit. ACLs and exclusive-lock scope are checked on acquisition (including retained ranges when adding new ones), renewal, and read-permit issuance. A revoked reader can finish using an already-issued short permit until it expires (under 1 second).

## Cached reads without a network call per block

When this daemon holds a live exclusive publication lease, local SMB range checks and the local range lease deadline suffice: the backend cannot grant a conflicting remote range. The publication coordinator serializes this admission with final-close release.

Read-only handles otherwise obtain a positive, fenced, one-second read permit from the metadata authority. The authority refuses exclusive range grants to another handle until that permit expires. The daemon uses a monotonic 900 ms deadline measured from request start, rechecks application range validity before using the permit, and releases permits on close/disconnect/shutdown. Ordinary writer leases remain available while a read permit is held, preserving read-while-editing behavior. If another exclusive range exists elsewhere on the inode, disjoint reads remain possible but use individual authoritative checks instead of a whole-inode permit.

A permit response arriving after its local deadline cannot authorize bytes or enter the cache. The daemon releases that grant and may request a fresh read permit, sharing the same three-attempt limit and 100/250 ms backoff used for transient read-admission transport failures. Each attempt gets a new request-start deadline, and existing application-lock authority is checked again after cleanup and before retry. Conflicts, stale fences, revoked access, expired application locks, writes, and lock mutations are never retried by this recovery path. This prevents a single slow metadata response from becoming an unnecessary lock failure while preserving fail-closed behavior when fresh authority cannot be obtained.

An exclusive LOCK can therefore encounter transient contention for up to 1 second even when the reading application has no explicit range lock. A failed exclusive acquisition prevents fresh read-permit renewal for 1.5 seconds, so a retrying locker is not perpetually postponed by a busy reader. LOCK remains nonblocking; applications must retry contention. There is no server-side wait queue or SMB pending-lock cancellation implementation yet. Named streams currently share the base inode's lock domain, which is conservative rather than independent per-stream locking.

Read-permit caching avoids a request for every block, but active read handles still need periodic authority renewal. Conflicting locks can force narrower checks and add network latency. No application throughput guarantee follows from this optimization.

Offline reads of the live mount cannot keep using an expired permit when the metadata authority is unreachable. The explicit offline/checkpoint and snapshot adapters remain read-only views with their own semantics; this protocol does not promise unlimited disconnected live reads while enforcing remote exclusive locks.

## Deployment

Deploy the matching gateway before this native build. The filespace schema includes `range_locks`, `read_permits`, `range_waiters` and device-bound `open_handles`. These tables and their expiry indexes migrate during the existing idempotent constructor migration. No data-file rewrite or external database migration is required. Older native versions do not enforce the new read-range/open-handle protocols; upgrade all collaborating clients before treating cross-device range reads and sharing as protected.

## Open-file lifetime and replacement

Each SMB handle now registers its read/write/delete access and sharing mask with the metadata authority. These checks are bidirectional: the new handle must permit existing access and every existing handle must permit the new access. Open references retain file bytes, named streams and history after unlink or backend rename-overwrite, while the old inode immediately disappears from the namespace. A retained handle still belongs to its authenticated user/device and still requires current ACL authorization. It cannot expose the old inode through a normal directory listing or authorize access after its permissions are revoked.

The native open coordinator requests 90-second references and uses a conservative 85-second monotonic deadline. Renewals are bounded to batches of 128; the backend caps lifetime at 120 seconds. These references are separate from the 60-second writer/range leases above. Closing a dirty handle flushes before releasing its retention reference. Shutdown leaves unresolved dirty references to expire rather than immediately discarding backend retention. Volatile handles are not restored from metadata backups. Once a local I/O check observes expiry, that failure is sticky even if a successful renewal response was already in flight; reopening requires a new handle. A regression covers this actor-reentrancy race.

macOS caches pathnames through SMB vnode identities. Remote replacement uses a presentation epoch to make a fresh pathname lookup see the replacement while an existing handle retains the displaced inode. Normal canonical IDs remain stable across lookup order/remount, but replacement presentation epochs are process-local and can change identity across remounts. Do not treat a presentation ID as a permanent cross-device identifier.

Host/VM tests exercised replacement, retained descriptors and rapid consecutive saves. Finite successful observations do not prove POSIX atomicity at every instant or compatibility with every app. See [Compatibility](../docs/COMPATIBILITY.md) for qualified workflows and remaining limits.

## Validation

`DistributedRangeTests` cover exact wire offsets/fences, close cleanup, sticky loss, late permit responses, read-permit expiry, and the latency/request-count fast paths. Backend `range-locks.test.ts` exercises independent clients, shared/exclusive conflicts, exact unlock, expiry/stale fences, publication isolation, ACL revocation, and non-starving read permits. `DistributedLeaseTests` use two independent real HTTP gateway clients authenticated as the same user, including simultaneous local handle acquisition, final-handle release, stale-fence renewal, a late old-owner release, and explicit recovery refusing active editors. Gateway wire tests cover the client header, fenced release, declared-inode upload authorization, and typed lock conflicts. SMB tests exercise conflicting ranges across two separate TCP sessions, connection-disconnect cleanup, atomic multi-range acquisition, and discovery of remotely created children.

Applications that hold unnecessary writable handles can prevent another editor from opening the same file until those handles close. Native macOS POSIX `fcntl` record locks return `ENOTSUP` on the tested SMB mount. Explicit exclusive SMBFS byte ranges and `flock` were exercised on the host and VM; shared range coexistence, blocking waits and fairness through every macOS application are not established. Named streams currently share their base inode's locking domain.
