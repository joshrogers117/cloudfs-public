# Keep files and folders on this Mac

`pin` records durable intent before starting background downloads. Cold folders return `cacheState: "pinning"` promptly. The engine walks every listing page and nested directory by opaque inode identity, resolves the current block manifests, and reserves the complete block membership in the cache before any download begins. Downloads use the transfer engine's bounded connection pool. Already-prefetched files can immediately return `"pinned"`.

Pinned data reserves at most 80% of the cache, including expected missing blocks. If a requested folder will not fit, its intent remains visible with `failureReason`; it does not silently become a successful pin. Increasing the cache size retries failed or incomplete pins. `pin.list` exposes per-pin logical content byte counts, resident block counts, and the optional failure reason. Cache-wide used/pinned bytes measure actual encrypted storage, so compression and encryption overhead can make those figures differ from per-pin content sizes.

The engine checks the namespace change feed every five seconds while connected, rewalks changed pins, and also checks permissions/membership periodically. Restricted accounts traverse only their explicitly granted mount roots. A refresh replaces the exact pinned block set: newly created children download automatically, modified files replace their old blocks, and removed children release their obsolete pin references. Failed refreshes retain previous cached content and show the error. A removed/revoked pin root releases its cache membership and leaves a visible failed intent that the user can remove.

Intent records live in `pin-intents-v2.json` in the daemon's stable per-filespace state folder and include the current display path, actual inode identity, recursive flag, and latest error. Legacy `pin-intents.json` is migrated on first load. The stable intent file and pending-write journal stay in place when downloaded blocks move. The daemon atomically saves per-filespace cache location/size in `cache-preferences.json`; relocation retains the source until that map and its parent directory have passed explicit durability barriers. An inode-based intent follows the same folder after a rename and refreshes its display path and Finder association. Mounted top-level grant aliases stay stable until remount, matching the volume's actual paths; ordinary descendant renames update dynamically. Removing a pin cancels its background work and increments its identity generation. Cache publication and unpin are serialized, so late downloads cannot resurrect a removed pin.

The macOS data-path content-policy entry point uses the same intent manager. `evict` first removes matching explicit pin intents, then releases eligible cached blocks. Cache clearing continues to retain pinned content.

Tests cover paginated recursive traversal, remote creation/modification/deletion, a delayed download racing unpin, cache-headroom rejection and retry, restart restoration, and a folder-only account's projected mount root.

Cache relocation rejects nonempty destinations belonging to other data, nested source/destination folders, and relative paths. If saving the location map fails before publication, the engine rolls the cache back to its retained source. A durability failure after publication keeps both copies and the newly published location. Tests reopen the relocated cache and resized budget after daemon restart, confirm pin intent restoration, and export pending writes from the unchanged original journal.


Offline reopen is now a separate checkpoint state. `offlineReady` is true only after the complete pinned subtree, encrypted manifests, named streams and cached payloads have been verified and an authorized feed fence confirms capture consistency. The app shows expiry and a read-only offline-open action. A resident pin can still have `offlineReady=false`, with an independent preparation error. See [the control API](CONTROL-API.md#offline-copies) for the 24-hour policy, identity binding, limits and mount selection. Offline mounts do not accept writes or silently fetch absent data.
