# Retained blocks for conflict recovery

A Mac's durable write journal stores the original committed block manifest and its changed local blocks. Unchanged original bytes can be absent from its downloaded cache after eviction or restart. Another Mac publishing a new version must therefore not make those original object keys unreadable or garbage-collectible.

Schema 15 adds `retained_blocks`, keyed by immutable inode and object key. A successful manifest replacement records the previous committed ownership before dropping live references, after version checks. The write is synchronous with the manifest publication. The migration also imports server-recorded snapshot references for live inodes; versions already overwritten before this upgrade without a snapshot cannot be reconstructed by guessing.

GET and HEAD presigns iterate current and retained ownership and check the inode's current ACL inside one Durable Object turn. They never trust a client-declared read inode. Multiple namespace references to a deduplicated key are checked until one readable owner is found. A move into an inaccessible folder, an expired or revoked grant, or a deleted inode denies new download URLs. Previously issued URLs remain valid until their signed expiration.

The collector excludes hashes held by retained recovery references. Live and snapshot reference counts keep their existing accounting; recovery references are separate GC roots. Restoring a snapshot records the version it displaces, so a pending editor can still export that original image. Deleting an inode or subtree removes its recovery references, while any snapshot's references continue protecting the snapshot bytes. A same-name recreated file has a new inode; it gains no old recovery access. A client facing deletion or revoked permission keeps its journal and reports the failed export rather than substituting current bytes or zeros.

Schema 16 adds a known-object catalog and server-issued PUT claims. Manifest publication checks object provenance and target write permission in the same SQL turn. A scoped writer cannot attach another folder's known private or historical key to an editable file to obtain a read URL. New keys require a matching principal/inode PUT claim. The claim does not permit GET before a successful manifest commit. PUT checks include historical ownership too, preventing direct overwrite through a declared unrelated inode. Catalog entries survive namespace deletion so retired keys cannot be claimed as unknown objects.

A PUT claim authorizes publication for seven days. Its original principal can renew through a new presign; expiration does not free the key for a different principal or inode. Claims are removed when their object is committed. Uncommitted claims and known-object catalog entries remain until filespace purge, because removing identity evidence before the corresponding bucket bytes are securely deleted would reopen the claim attack. Administrators retain the explicit legacy direct-ingestion seam for genuinely unknown objects; bucket contents introduced outside the gateway are an operator-managed import, not a scoped-user upload.

Retention deliberately has no automatic time or version cap while the original inode remains live. Metadata stores unique inode/object pairs, not a full manifest for every save. Old payload storage still grows with unique replaced blocks, and the catalog grows with unique object keys. There is no automatic recovery-history cleanup or version-history browsing UI. A future retention feature must coordinate outstanding journals before releasing their base blocks; silently expiring them would turn acknowledged partial edits into unrecoverable data.

The gateway authorizes metadata and URLs; it does not proxy or inspect each uploaded object before publication. Clients verify ciphertext SHA-256 and authenticated decryption before using data. A valid PUT claim is upload authority, not proof that a malicious uploader sent correct bytes. ACLs and scope remain necessary at commit even after a URL was issued.

Validation includes actual Worker routes for old-version GET/HEAD, batch minting, unknown-key declarations, moves/revocation, deletion/recreation, deduplicated owners, and forbidden manifest/PUT claims. SQLite tests exercise snapshot restore, independent reference accounting, recursive cleanup, CAS rejection, and idempotent migration. A real two-daemon Worker/MinIO test exports a partial edit after a conflicting remote block change and a restart with the downloaded cache removed; the complete original-plus-local image must match SHA-256, with failures retaining every journal byte.
