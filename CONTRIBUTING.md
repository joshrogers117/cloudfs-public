# Contributing to CloudFS

Contributions are licensed under [AGPL-3.0-or-later](LICENSE). Keep changes focused, document changed behavior, and use regression tests where they protect meaningful behavior.

This guide's full contributor validation gate is for a clone of the public source
repository. The curated server archive supports the documented build and deploy
paths in [Build CloudFS](docs/BUILD.md); it does not include the full repository
test harness.

## Development setup

Use Node.js 22.12+ and npm. Native work also needs macOS, Xcode with Swift 6.1+ and XcodeGen.

```sh
npm ci --prefix backend
npm ci --prefix web
npm ci --prefix cli
cp backend/.dev.vars.example backend/.dev.vars
```

Replace the `STORAGE_ENC_KEY` placeholder in the ignored `.dev.vars` with a new local value generated by `openssl rand -base64 32`. The other example values are public development credentials. Never deploy them.

```sh
bash scripts/check-project.sh
npm --prefix cli run typecheck
npm --prefix cli test
swift test --package-path cloudfsd
swift test --package-path client-app
```

The backend tests run in the local Workers runtime. The default Swift suites skip opt-in live mount tests; a passing unit suite does not establish live backend or editing-app compatibility. See [build instructions](docs/BUILD.md), [mount architecture](cloudfsd/MOUNT.md) and [qualification coverage](docs/COMPATIBILITY.md).

For local servers, use `npm --prefix backend run dev` and `npm --prefix web run dev`. Use an isolated named deployment profile for live tests. Do not change a shared server or use its data as a test fixture.

## Source and documentation

- `backend/`: Worker gateway and Durable Objects; [HTTP contract](backend/API.md).
- `web/`: browser setup and console.
- `cloudfsd/`: Swift engine; [local control contract](cloudfsd/CONTROL-API.md).
- `client-app/`: SwiftUI app and Finder extension.
- `cli/`: command-line client.
- `scripts/`: installer, operations, validation and release tools.

Update the relevant contract and user guide with behavior changes. `node scripts/check-docs.mjs` checks local Markdown links. Keep current instructions in one canonical guide; do not add dated status dumps or copy private test transcripts into the repository.

The release gate also checks shipped branding, script tests, backend type checking/tests, console tests/lint/build and whitespace. Match existing code style and add an `SPDX-License-Identifier: AGPL-3.0-or-later` comment to new source files where the format permits it.

## Credentials and reports

Keep deployment profiles, secrets, signing configuration, caches and generated artifacts in ignored locations. Review `git diff --cached` before committing. Do not include personal account data, private server addresses, invitation URLs or Keychain exports in fixtures or reports. Public example addresses and disposable fixtures should use reserved example domains.

Report security issues privately through [SECURITY.md](SECURITY.md). Ordinary bugs belong in [GitHub Issues](https://github.com/joshrogers117/cloudfs-public/issues), with versions, reproduction steps and redacted diagnostics.

## Pull requests

Use a branch for each change. Explain the concrete behavior change, relevant verification and remaining limitations. Keep the build/test commands above green for affected components. Public commits may use your GitHub-provided noreply address; no personal email address is required.

Signed distribution and publication are maintainer operations described in [Publishing](docs/PUBLISHING.md). Never substitute a locally unsigned build for the released app without clearly labeling it as a development build.
